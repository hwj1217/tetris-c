# 終端機版 Tetris（C 語言實作）

用 C 語言搭配 ncurses 寫的終端機俄羅斯方塊。這是在完成 C 語言的動態記憶體、struct、記憶體佈局、多檔案專案等主題之後，作為綜合練習的專案。

## 功能

- **方塊移動與碰撞偵測** — 可左右下移動，會被牆壁與已堆疊的方塊擋住
- **自動重力下落** — 方塊依計時器自動落下，也可手動快速下移
- **旋轉** — 每種方塊有 4 種旋轉狀態（座標依據 SRS）
- **消行** — 整行填滿即消除，上方所有行往下遞補
- **隨機生成方塊** — 每次於頂端隨機生成一種新方塊
- **計分與顯示** — 每消一行得 100 分，即時顯示於盤面旁
- **方塊顏色區分** — 7 種方塊各有專屬顏色
- **遊戲結束判斷** — 當新方塊無法生成時遊戲結束

## 編譯與執行

### 相依套件

本專案需要 ncurses 開發套件。

Debian/Ubuntu 系（含 Kubuntu）：

```bash
sudo apt install libncurses-dev
```

### 編譯

```bash
gcc -Wall -Wextra -o tetris main.c -lncurses
```

### 執行

```bash
./tetris
```

### 操作按鍵

| 按鍵 | 動作 |
|-----|--------|
| `←` | 向左移動 |
| `→` | 向右移動 |
| `↓` | 手動下移一格 |
| `↑` | 順時針旋轉 |
| `q` | 結束遊戲 |

## 架構設計

### 單一真相來源（Single source of truth）

所有畫面繪製與碰撞判斷，都只讀取同一個 `board[20][10]` 陣列。掉落中的方塊在每次移動時都會寫回 `board`，因此這個陣列永遠反映真實的遊戲狀態。

早期版本曾經直接從 `all_pieces` 查表資料繪製方塊，碰撞判斷卻讀取 `board`。當資料來源有兩個時，只要其中一邊漏了更新，玩家看到的畫面就會和遊戲邏輯的判定不一致——這類 bug 特別難發現，因為程式編譯得過，看起來也大致正確。

### 基準點 + 相對偏移量

每個方塊的位置以一個基準 `Point` 表示，其餘四格則從 `all_pieces[type].rotations[rotIndex]` 查表取得相對偏移量。方塊移動一格時，只需更新 `base.row` 與 `base.col` 這 2 個數字，而不是四組絕對座標所需的 8 個。

需要手動維護的數字越少，寫錯的機會就越低。`clear_piece` 早期的一個 bug 正是如此：複製貼上的那一行誤用了 `base.row`，實際上應該是 `base.col`。

## 除錯記錄

以下這些 bug 都是「編譯乾淨、但行為不正確」的類型——只有實際執行並觀察程式行為時才會浮現。

### 1. 新方塊在生成後有一格畫面看不見

**現象。** 方塊鎖定之後，下一個方塊要等一個 tick 才出現，而且出現時已經比它的生成位置低了一格。

**原因。** 生成分支把新的 `Fall` 指派給 `game.current`，卻沒有呼叫 `place_piece`，導致新方塊只存在於遊戲狀態中，沒有被寫進 `board`。而所有繪製都是讀取 `board`，所以畫面上沒有東西可畫。

**修法。** 在指派新方塊之後，立刻呼叫 `place_piece`。

**心得。** 每一個會改變 `current` 的分支，都必須同步更新 `board`。三個移動分支原本就遵循 `clear_piece` → 更新 → `place_piece` 的模式，生成分支卻只做了中間那一步，破壞了這個模式。

### 2. 加入堆疊碰撞檢查後，方塊完全不再下落

**現象。** 在 `is_valid_position` 加入 `board[row][col] != EMPTY` 檢查之後，方塊完全不會往下掉——不是掉到一半卡住，而是連一格都動不了。每個 tick 都被判定不合法，於是立刻生成新方塊，舊方塊則停在原地不動。

**原因。** 重力分支呼叫 `is_valid_position` 的時機在 `clear_piece` **之前**，與其他三個移動分支相反。檢查的當下，方塊自己的四格資料還留在 `board` 上，新的佔用檢查無法分辨「這格屬於別的方塊」和「這格是我自己現在站的地方」。以 `base = (5, 5)` 的 T 型方塊為例，目前佔用 `(5, 6), (6, 5), (6, 6), (6, 7)`，往下移一格後會佔用 `(6, 6), (7, 5), (7, 6), (7, 7)`。重疊的那格 `(6, 6)` 使得每一次移動都被判定不合法。

**修法。** 把重力分支調整成先 `clear_piece`，與其他三個分支一致。而「不合法」的路徑需要多做一步：先呼叫一次 `place_piece`，把**舊方塊**畫回原本的位置——這正是「鎖定」的實際動作——之後才把 `current` 切換成新方塊並繪製。

```c
clear_piece(&game);
if (is_valid_position(&game, game.current.base.row + 1, game.current.base.col, game.current.rotIndex)) {
    game.current.base.row += 1;
    place_piece(&game);
}
else {
    place_piece(&game);              // 鎖定舊方塊
    game.current = (Fall){ ... };    // 然後才生成新方塊
    place_piece(&game);
}
```

**心得。** 同一個函式，在不同的呼叫時機會給出不同的答案。`is_valid_position` 本身從來沒有錯，錯的是提問的時機——提問時，`board` 上還留著那個正在發問的方塊。

### 3. 連續多行同時填滿時只消掉一半

**現象。** 四行連續填滿的情況下，`clear_lines` 只消除了其中兩行，另外兩行仍留在盤面上。

**原因。** 掃描使用 `for (int row = 19; row >= 0; row--)`，每一輪都會自動遞減 `row`。但消除一行會讓上方所有行往下移一格，因此處理完 row 19 之後，`board[19]` 裝的是原本 row 18 的內容——一份全新的、從未被檢查過的資料。此時迴圈已經跳到 row 18，永遠不會回頭。

**修法。** 把 `for` 迴圈改成 `while` 迴圈，手動控制遞減。如果這一行沒滿，就往上移動；如果滿了，消除後停留在同一個 index，讓剛遞補進來的那一行也能被檢查到。

```c
int row = 19;
while (row >= 0) {
    // ... 檢查這一行是否填滿 ...
    if (isFull) {
        // ... 將上方所有行往下移一格 ...
        lines_cleared += 1;
        // 這裡不做 row--：重新檢查同一個 index
    }
    else {
        row--;
    }
}
```

**心得。** `for` 迴圈的自動遞增（減）建立在一個前提上：一輪結束後，這個 index 就處理完了。但當迴圈本身會改動它正在走訪的資料時，這個前提就不成立。同樣的陷阱也會出現在從陣列中移除元素，或是 C++ 中的 iterator invalidation。

## 尚未實作

與標準 Tetris 相比，目前已知還缺少的功能：

- **Wall kick** — 靠牆或貼著堆疊旋轉時，目前只是直接失敗，不會把方塊往旁邊推開
- **下一個方塊預覽** — 尚未顯示即將生成的方塊
- **關卡等級與變動落下速度** — 重力目前固定為 500 ms，不隨分數改變
- **Hard drop** — 目前只有手動下移（`↓`），沒有一次落到底的功能
- **Hold** — 無法暫存目前方塊留待後用
- **7-bag 隨機演算法** — 目前使用單純的 `rand() % 7`，因此同一種方塊可能連續出現多次
